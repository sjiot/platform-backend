## 중심 주장

AI는 쓰지 않는다. 논문은 다음 한 문장을 설명한다.

> 장비 간 연쇄 명령을 서버의 상태 기반 전량 명령으로 바꿔 폐루프를 구성했고, 그 위에서 시스템이 스스로 처리하는 범위와 사람이 개입하는 범위를 나눴다.

## 서론 (약 0.3쪽)

- **배경**: Physical AI가 실제 설비를 움직이려면 서버와 설비의 상태를 맞추고 고장을 감지하는 실행 계층이 필요하다.
- **선행 연구**: oneM2M 구독 기반 관제 (유태람 외, KICS 2026 동계) 두세 문장.
- **문제**: 초기 구현은 장비가 다음 장비에 직접 명령을 넘겨, 서버가 전체 상태를 알 수 없었다.
- **기여**: 명령을 서버로 일원화하고 모든 단계 전이를 장비 보고로만 일으키는 폐루프 구조를 구현했다. 그 위에서 자율 처리 범위와 사람 개입 범위를 나눴다.

## 본론 1. 기존 구조와 한계 (약 0.3쪽)

- **통신 방식**: 키오스크 → HTTP → Flask 서버 → Redis(현재 상태) / Mobius(장비 통신).
- **이전 컨테이너 구조**

  | 컨테이너 | 쓰는 쪽 | 읽는 쪽 | 역할 |
  |---|---|---|---|
  | `cnt_order` | 플랫폼 | 창고 (폴링) | 주문 내역 |
  | `cnt_table` | 플랫폼 | AGV (구독) | 조립대 상태와 AGV 출동 명령 |
  | `cnt_agv_command` | 플랫폼 | AGV (구독) | 인증, 노쇼, 취소 명령 |
  | `cnt_dispense` | 창고 | 플랫폼 | 불출 완료 보고 |
  | `cnt_stock` | 창고 | 플랫폼 | 재고 통짜 JSON |
  | `cnt_load` | AGV | 플랫폼 | 적재 완료 보고 |
  | `cnt_arrived_table` | AGV | 플랫폼 | 조립대 도착 보고 |

  창고는 불출을 마치면 AGV에 `order_id`와 `station_id`를 직접 넘겼다.

- **한계**
  - 장비가 전체 공정 순서를 알아야 한다.
  - 서버가 지시하면서 상태를 스스로 써 넣어, 실제 설비와 어긋날 수 있다.
  - 재고가 통짜 JSON 하나라 칸별 고장을 구분하지 못한다.

## 본론 2. 제안 구조: 폐루프 제어 (약 0.5쪽)

- **그림 1**: 이전과 현재의 명령·보고 경로를 좌우로 대비한다.
- **명령**: 진행 중 주문 전체를 `seq`와 함께 `cnt_process` 하나에 스냅샷으로 올린다. 장비는 공정 순서와 이전 상태를 기억하지 않는다. 내용이 같으면 올리지 않는다. (`services/process.py`)
- **보고**: 장비가 자기 컨테이너 44개에 결과를 올리고, 서버가 구독 알림으로 받아 Redis를 갱신한다. (`routes/callback.py`, `callbacks/`)
- **단계**: status 16값이며, 모든 전이는 보고를 받았을 때만 일어난다.

  ```text
  queued → assigned → keycap_dispensed → keycap_reached → keycap_packed
         → tray_reached → board_packed → pickup_reached → loaded → arrived
         → verified → received → completed
  ```

  곁가지 3개: `keycap_mismatched`, `board_mismatched`, `unclaimed`

- **표 1**: 이전과 현재 비교

  | 항목 | 이전 | 현재 |
  |---|---|---|
  | 명령 주체 | 플랫폼과 장비 (다음 팀 호출) | 플랫폼 단독 |
  | 장비가 아는 것 | 전체 공정 순서 | 자기 동작 하나 |
  | 명령 채널 | 3개 | `cnt_process` 1개 |
  | 장비 간 직접 전달 | 있음 (창고 → AGV) | 없음 |
  | 보고 컨테이너 | 4개 | 44개 (재고 36 + 동작 8) |
  | 서버 상태 갱신 근거 | 서버가 지시하며 직접 기록 | 장비 보고 수신 |

## 본론 3. 자율 범위 (약 0.5쪽)

논문의 중심 절이다. 기준은 **"시스템이 스스로 복구하면 status, 사람이 와야 하면 fault"** 이다.

### 표 2-1. 시스템이 스스로 처리하는 것

| 상황 | 처리 | 코드 |
|---|---|---|
| 오배출 | `keycap_mismatched` / `board_mismatched`로 전이, 부족분만 재출고 (최대 2회) | `callbacks/warehouse.py`, `services/collector.py` |
| 노쇼 | `unclaimed`로 종료, AGV가 폐기를 보고하면 조립대 자동 해제 | `services/archive.py`, `callbacks/agv.py` |
| 조립 시간 초과 | `completed`로 자동 종료 | `services/watchdog.py` |
| 재고 소진·선반 고장으로 막힌 주문 | 건너뛰고 뒤 주문을 먼저 배정 | `services/dispatch.py` |
| 재고 복귀·드라이버 정상 보고 | 차단을 풀고 밀린 주문을 자동 재배정 | `callbacks/warehouse.py`, `services/dispatch.py` |
| AGV가 앞 주문에 묶여 있음 | AGV 보고 1건마다 대기 주문의 마감을 10초 연장 (오탐 방지) | `services/watchdog.py` |

### 표 2-2. 사람이 개입하는 것 (fault 17종)

| 구분 | fault |
|---|---|
| 컨베이어 4 | `keycap_01_belt_jammed`, `keycap_02_belt_jammed`, `tray_01_belt_jammed`, `tray_02_belt_jammed` |
| 카트리지·선반 3 | `keycap_cartridge_failed`, `board_cartridge_failed`, `keycap_driver_failed` |
| 로봇팔 3 | `keycap_pack_failed`, `board_pack_failed`, `tray_load_failed` |
| AGV 3 | `pickup_failed`, `drop_failed`, `agv_broken` |
| 재고 2 | `keycap_empty`, `board_empty` |
| 서버 2 | `stage_timeout` (보고 끊김), `restart_unknown` (복구 근거 없음) |

- **fault 처리 원칙**: 단계는 그대로 두고 fault와 위치(`fault_section`)만 기록한다. 관리자가 해제하면 그 자리에서 이어진다. (`services/process.py`)
- **상태 복구**: 서버가 상태를 잃으면 관리자 리셋으로 `cnt_process` 최신 스냅샷과 배출 기록에서 진행 중 주문을 되살린다. 대기열은 복구되지 않고, 근거가 없는 구간은 추측 대신 `restart_unknown`으로 세운다. (`services/recovery.py`)

2쪽에 두 표를 모두 넣기 빠듯하면 2-2는 구분별 개수만 남기고 fault 이름은 포스터에 싣는다.

## 본론 4. 동작 확인 (약 0.2쪽)

- **표 3**: 장비 보고 수신부터 다음 명령 CIN 생성까지 걸린 시간 (p50, p95, 표본 수). 워커 수 비교는 여기에 한 줄로 넣는다.
- **환경**: 리눅스 서버 사양, 로컬 Mobius, 장비 구성 한두 줄.
- 여유가 있으면 고장 주입 후 감지까지 걸린 시간을 추가한다.

|---|---|

## 결론 (약 0.2쪽)

- **요약**: 명령 일원화와 보고 기반 전이로 폐루프를 구성했고, 자율 처리 6종과 사람 개입 17종을 구분했다.
- **한계**: 대기열 3건의 소규모 라인이다. 명령 유실 시 주기 재전송은 아직 구현하지 않았다. 상태 복구는 관리자가 시작한다.
- **향후**: 규칙 기반 배정을 학습 기반 스케줄러로 바꿔도 명령 형식(`cnt_process`)은 그대로 쓸 수 있다.

## 표현 주의

| 피할 표현 | 쓸 표현 | 이유 |
|---|---|---|
| 이전 구조는 개루프였다 | 서버를 거치지 않는 명령 경로가 있어 고리가 서버에서 닫히지 않았다 | 이전에도 보고 컨테이너가 4개 있었다 |
| 자율형 CPS 구조를 완성했다 | 폐루프 제어 구조를 구현했다 | 사람이 개입하는 fault가 17종 남아 있다 |
| 장비는 PC가 필요 없다 | 장비는 전체 공정 순서와 이전 상태를 기억할 필요가 없다 | 창고 PC가 실제로 있다 |
| 유실된 명령은 다음 스냅샷으로 복구된다 | 명령을 놓친 장비는 단계 마감으로 감지한다 | 주기 재전송(`periodic=True`)을 호출하는 곳이 없다 |
| TTL을 주기적으로 늘린다 | AGV 보고 1건마다 단계 마감을 10초 연장한다 | 주기가 아니라 보고 수신 시점이고, 대상은 픽업대에서 기다리는 다음 주문이다 |
| 오탐 탐지 | 오탐 방지 | 잘못된 고장 판정을 막는 기능이다 |
| 작업이 수월해졌다 | 장비는 `cnt_process` 하나만 구독한다 | 개발 편의는 측정한 적이 없다 |
| AI 기반, 지능형 | 규칙 기반 | AI를 쓰지 않는다 |

## 내부 문서(9월)와 현재 코드의 차이

표와 값을 옮길 때 현재 코드를 따른다.

| 항목 | 내부 문서 | 현재 코드 |
|---|---|---|
| 재보충 목록 | `key_restock`, 수량 임계 이하인 칸 | `keycap_restock`, 관리자가 채웠고 창고가 아직 반영하지 않은 칸 |
| `cnt_order` 기록 시점 | 주문 종료 시 | 배정 시 |
| 주문 TTL | 1시간 | 진행 중 24시간, 종료 후 10분 |
| AGV fault | `agv_collided` 포함 | 없음 |
| 카트리지 fault | 2종 | `keycap_driver_failed` 추가로 3종 |
| 서버 fault | `stage_timeout` 1종 | `restart_unknown` 추가로 2종 |
| 도착 시각 | `station:arrived_at:{id}` 키 | `order:{id}` 해시의 `arrived_at` 필드 |
| `stats:*` 집계 | 있음 | 폐기 (아카이브에서 계산) |
