# 개선 후보

아래의 효과는 모두 가설이다. 왕복 수 외에는 측정값이 없다.

## 현재 호출 수

`9ec25a8` 기준 코드를 가짜 Redis와 가짜 Mobius로 실행해 셌다. 왕복 수는 환경과 무관하게 코드 경로로 정해지지만, 리눅스 서버에서 `python -m infra.latency_report --by-request`로 다시 확인한다. 시간은 이 실험으로 알 수 없다.

| 경로 | Redis 왕복 | 서버가 만든 CIN |
|---|---:|---|
| `try_assign_next`: 막힌 주문 없음 | 50 | `cnt_process`, `cnt_order`, `cnt_station` |
| `try_assign_next`: 앞에 막힌 주문 1건 | 59 | 위와 같음 |
| `try_assign_next`: 앞에 막힌 주문 2건 | 68 | 위와 같음 |
| `set_stage`: 진행 주문 1건 | 20 | `cnt_process` |
| `set_stage`: 진행 주문 2건 | 21 | `cnt_process` |
| `set_stage`: 진행 주문 3건 | 22 | `cnt_process` |
| `cnt_keycap_dispense` 콜백: 1~3번째 | 4 | 없음 |
| `cnt_keycap_dispense` 콜백: 4번째 | 24 | `cnt_process` |
| `cnt_keycap_status` 콜백: 무관한 칸, 변화 없음 | 11 | 없음 |
| `push_process`: 내용 동일로 생략 | 7 | 없음 |

`set_stage`(진행 주문 1건) 20회의 구성:

| 구간 | 왕복 |
|---|---:|
| 이전 단계 읽기, 단계 쓰기 | 2 |
| `_touch_order` | 8 |
| 워치독 마감 등록 | 1 |
| `push_process` 읽기 | 7 |
| `process:seq`, `process:last` 쓰기 | 2 |

왕복 수는 호출 시점의 상태에 따라 달라진다. 예를 들어 `_touch_order`는 존재하는 키에만 `EXPIRE`를 보낸다.

## 네트워크

### A. Mobius 연결 재사용

| 항목 | 내용 |
|---|---|
| 현재 | `_timed_request`가 `requests.request`를 호출한다. 호출마다 세션을 새로 만들고 닫는다 |
| 변경 | `requests.Session`을 재사용한다 |
| 가설 | TCP·TLS 연결 비용이 빠져 `mobius_write` p50이 줄어든다 |
| 지표 | `mobius_write`, `mobius_read` p50/p95, 실패율 |
| 실험 환경 | 실제 Mobius + 테스트 전용 컨테이너. 가짜 Mobius로는 TLS 비용을 잴 수 없다 |
| 위험 | 서버가 끊은 유휴 연결 재사용 시 오류. 연결 풀은 워커별로 만들고 재시도 정책을 정해야 한다 |

사전 확인: 리눅스 서버에서 `curl -w`로 연결 단계별 시간을 본다. TLS 시간이 전체에서 작으면 이 후보의 효과도 작다.

### B. Redis 왕복 묶기

| 항목 | 내용 |
|---|---|
| 현재 | `_touch_order`가 `EXISTS`, `EXPIRE`를 키마다 보낸다. `_build_body`도 조회를 하나씩 보낸다 |
| 변경 | 파이프라인으로 묶는다. 재고 전체 조회의 중복 호출도 줄인다 |
| 예상 | `_touch_order` 8 → 1회, `push_process` 읽기 7 → 2회. `set_stage`는 20 → 약 8회. 구현 후 실측으로 확정한다 |
| 지표 | 요청당 왕복 수, 요청당 Redis 시간 합계 |
| 위험 | 트랜잭션 파이프라인과 비트랜잭션 파이프라인의 차이. 읽은 값으로 분기하는 코드는 묶을 수 없다 |

Redis가 서버와 같은 기기나 LAN에 있으면 왕복이 줄어도 시간 절감은 작을 수 있다. 이 경우 왕복 수 감소만 사실대로 보고하고, 중심 결과로 삼지 않는다.

### C. 기록용 CIN 비동기화

| 항목 | 내용 |
|---|---|
| 현재 | `_assign`이 CIN 3건을 순서대로 보낸다. `cnt_order`, `cnt_station`은 코드 주석상 기록용이다 |
| 변경 | `cnt_process`는 동기로 두고 기록용 2건은 백그라운드 큐로 보낸다 |
| 가설 | 배정 처리 시간에서 Mobius 대기가 약 3건에서 1건으로 줄어든다 |
| 지표 | 배정을 일으킨 요청의 처리 시간, 동시 콜백의 대기 시간 |
| 실험 환경 | 실제 Mobius와 가짜 Mobius 양쪽 |
| 위험 | 프로세스가 죽으면 큐에 남은 기록이 사라진다. 재시도와 순서 보장을 정해야 한다 |

**`cnt_process`는 비동기로 바꾸면 안 된다.** 전송 실패를 근거로 배정을 롤백하기 때문이다(`dispatch._assign`).

**먼저 확인할 것:** `_dispatch_order` 설명에는 "불출 지시"라고 되어 있고 `_assign` 주석에는 "기록"이라고 되어 있다. 코드 안에는 구독자가 드러나지 않으니 창고팀에 `cnt_order`를 쓰는지 확인한다.

### D. 워커 수 조정

| 항목 | 내용 |
|---|---|
| 현재 | `Dockerfile` 기준 gunicorn 기본값인 sync 워커 1개다. 리눅스 서버의 실행 설정은 확인 필요 |
| 변경 | 워커 또는 스레드 수를 늘려 비교한다 |
| 지표 | 대기 추정 시간(클라이언트 응답 시간 - `callback_handle`), p95 |
| 도구 | `python -m infra.latency_burst` |
| 위험 | 동시 콜백에서 경쟁 상태가 생길 수 있다. 현재 코드는 읽고 판단한 뒤 쓰는 부분이 많아 정합성 시험이 함께 필요하다 |

## 알고리즘

### E. 막힌 주문 건너뛰기

| 항목 | 내용 |
|---|---|
| 비교 | `SKIP_BLOCKED=True` / `SKIP_BLOCKED=False` |
| 가설 | 재고 부족이 있을 때 건너뛰기가 처리량을 높이고 평균 대기를 줄인다. 막힌 주문의 최대 대기는 늘어날 수 있다 |
| 지표 | 처리량, 평균·최대 대기 시간, 조립대 가동률 |
| 시나리오 | 재고 충분, 인기 칸 소진, 드라이버 고장을 나눈다. 주문 도착 간격과 대기열 3건 제한도 고정한다 |
| 실험 환경 | 시뮬레이터. 기계 시간은 실제 장비 측정값을 쓴다 |

재고가 충분하면 두 정책의 결과가 같아야 한다. 이 경우를 시뮬레이터 검증에 쓴다.

왕복 비용도 함께 보고한다. 막힌 주문 1건당 `try_assign_next` 왕복이 9회 늘어난다.

### F. AGV 게이트 제외

| 항목 | 내용 |
|---|---|
| 비교 | 현재 방식 / AGV 유휴를 배정 게이트에 추가 |
| 가설 | AGV를 게이트에 넣으면 앞 주문이 조립대에 머무는 동안 창고가 놀아 처리량이 떨어진다 |
| 지표 | 처리량, 전체 완료 시간, 조립대 가동률, 창고 유휴 시간 |
| 실험 환경 | 시뮬레이터. 비교용 게이트 구현이 필요하다 |

고객의 조립 시간과 노쇼 비율이 결과를 크게 바꾼다. 값을 바꿔 민감도를 함께 본다.
