# 실험 계획

운영과 테스트를 모두 리눅스 서버에서 한다. 비교 실험은 같은 서버, 같은 설정으로 돌린다.

## 1. 환경 기록

논문의 실험 환경 표에 쓴다. 실험마다 아래 명령으로 JSON을 남기고, 자동으로 안 잡히는 값은 직접 채운다.

```bash
python -m infra.latency_env --run-id A-session-r1 --gunicorn "-w 1"
```

서버 준비는 다음 순서로 한다. `.env`는 git에 없으므로 직접 옮긴다.

```bash
git clone -b lgk-refactor <저장소 주소> && cd <저장소 폴더>
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
LATENCY_LOG=1 LATENCY_RUN_ID=baseline-r1 gunicorn -w 1 -b 0.0.0.0:8080 'app:create_app()'
```

`logs/latency`에 쓰기 권한이 없는 실행 계정이면 `LATENCY_DIR`로 저장 폴더를 지정한다.

| 항목 | 값 | 확인 명령 |
|---|---|---|
| 배포판, 커널 | `[측정 필요]` | `cat /etc/os-release`, `uname -r` |
| CPU, 메모리 | `[측정 필요]` | `lscpu`, `free -h` |
| Python, gunicorn 버전 | `[측정 필요]` | `python --version`, `gunicorn --version` |
| gunicorn 워커, 스레드 수 | `[측정 필요]` | 실행 명령 또는 `systemctl cat <서비스>` |
| Redis 버전, 위치 | `[측정 필요]` | `redis-cli INFO server` |
| Redis 왕복 시간 | `[측정 필요]` | `redis-cli --latency` |
| Mobius까지 왕복 시간 | `[측정 필요]` | `ping`, `mtr --report` |
| 시각 동기화 상태 | `[측정 필요]` | `chronyc tracking` |
| 네트워크 | `[측정 필요]` | 유선/무선, 교내망 등 |

`ping`이나 `mtr`이 막혀 있으면 아래 `curl -w`의 연결 시간을 사용한다.

## 2. 실험 환경

| 환경 | 구성 | 쓸 곳 | 쓰면 안 되는 곳 |
|---|---|---|---|
| 실기 | 서버 + Mobius + 실제 장비 | 단계 분해, 현실 검증 | 통계 비교 (표본이 적다) |
| 실제 Mobius | 서버 + Mobius + 테스트 전용 컨테이너 | A, 시계 차이 측정 | |
| 가짜 Mobius | 서버 + 스텁 + 전용 Redis DB | B, C, D 부하 시험 | Mobius 네트워크 개선 수치 |
| 시뮬레이터 | 실제 서비스 코드 + 시간 모델 | E, F, G | 네트워크 시간 |

**실험 중 금지:** 테스트에서 실제 `cnt_process`에 쓰지 않는다. 장비가 움직일 수 있고 CIN이 플랫폼 기록에 남는다. 운영 Redis DB도 쓰지 않는다.

Mobius는 공용 서버이므로 부하 시험을 하기 전에 운영 측에 확인한다. 실제 Mobius 실험은 요청 간격을 두고, 빠른 연속 호출은 가짜 Mobius에서만 한다.

## 3. 공통 절차

1. 실행마다 `LATENCY_RUN_ID`에 후보, 조건, 반복 번호를 넣는다. 예: `A-session-r2`
2. 커밋 해시와 설정을 함께 기록한다.
3. 시작 전 Redis 전용 DB를 초기화하고 재고와 주문을 같은 상태로 맞춘다.
4. 앞부분 안정화 구간은 분석에서 뺀다. 뺄 구간을 미리 정한다.
5. 조건을 번갈아 돌린다. 예: 기존 → 개선 → 기존 → 개선
6. 조건마다 최소 300건을 3회 이상 반복한다. p95가 안정되지 않으면 늘린다.
7. 실행 중 다른 부하를 돌리지 않고, 가능하면 시간대를 나눠 반복한다.

## 4. 사전 측정

### 측정 부하

`LATENCY_LOG`만 끄고 켜서 같은 부하를 비교한다. ([02-metrics.md](02-metrics.md) 4장)

### Mobius 연결 단계 분해

후보 A에 앞서 리눅스 서버에서 실행한다. 쓰기 없는 GET을 대상으로 한다. API 키가 셸 기록에 남지 않게 환경 변수로 넣는다.

```bash
curl -s -o /dev/null \
  -H "X-API-KEY: $API_KEY" \
  -H "X-AUTH-CUSTOM-LECTURE: $LECTURE_ID" \
  -H "X-AUTH-CUSTOM-CREATOR: $CREATOR_ID" \
  -H "X-M2M-RI: paper-test" \
  -H "X-M2M-Origin: $ORIGIN" \
  -H "Accept: application/json" \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  "$MP_URL/$CB/$AE_RN/<테스트 컨테이너>/la"
```

연결 재사용 여부는 실행 중 `ss -tan | grep <Mobius 주소>`로 확인한다. 개선 후에는 같은 연결이 유지되어야 한다.

### 네트워크 조건 민감도 (선택)

가짜 Mobius를 쓰는 전용 환경에서 `tc netem`으로 지연을 넣어 조건별 결과를 볼 수 있다. 네트워크 설정을 바꾸는 명령이므로 운영 서버에서는 하지 않는다. 결과는 실측이 아니라 조건 모의로 표기한다.

## 5. 실험별 조건

| 후보 | 비교 조건 | 부하 | 주 지표 |
|---|---|---|---|
| A | `requests.request` / `Session` | 일정 간격의 테스트 CIN | `mobius_write` p50/p95, 실패율 |
| B | 개별 명령 / 파이프라인 | 시뮬레이터 주문 1건 전 과정 | 요청당 왕복 수, Redis 시간 합계 |
| C | 동기 3건 / 동기 1건 + 비동기 2건 | 배정 반복, 동시 콜백 | 배정 처리 시간, 대기 추정 시간 |
| D | 워커·스레드 수 변경 | `latency_burst.py` 동시 콜백 | 대기 추정 시간, 처리량, 정합성 위반 수 |
| E | `SKIP_BLOCKED` 참/거짓 | 재고 시나리오 3종, 시드 고정 반복 | 처리량, 평균·최대 대기 |
| F | AGV 게이트 없음/있음 | 조립 시간·노쇼 비율 변화 | 처리량, 완료 시간, 가동률 |
| G | 생략 사용/미사용 | 시뮬레이터 주문과 재고 콜백 | 주문당 CIN 수, 절감률 |

C에서 스텁의 지연은 실제 Mobius에서 측정한 `mobius_write` p50 값을 넣고, 이 값을 논문에 적는다.

## 6. 시뮬레이터

E, F는 시간 흐름이 필요하다. `tests/fakes.py`의 `Line`은 콜백을 순서대로 넣을 뿐 시간 개념이 없으므로 다음을 추가해야 한다.

- 이벤트 시각 순서로 처리하는 시뮬레이션 시계
- 실기에서 측정한 단계별 기계 시간 분포
- 주문 도착 간격, 조립 시간, 노쇼 비율, 재고 시나리오
- 재현을 위한 난수 시드 기록

서버 코드의 `time.time()`과 워치독 마감도 시뮬레이션 시계를 따라야 한다.

**실기 데이터가 부족하면** 기계 시간을 가정값으로 두고, 가정값임을 논문에 밝히며 값을 바꿔가며 결과가 유지되는지 확인한다.

## 7. 분석

- p50, p95, 최대값, 실패율, 표본 수를 함께 쓴다.
- 반복 실행 간의 차이를 함께 보여 준다. 차이 비율만 쓰지 않는다.
- 두 조건은 Mann-Whitney U 검정과 부트스트랩 신뢰구간으로 비교한다. 지연 시간은 정규분포를 따르지 않는 경우가 많다.
- 시간적으로 붙은 요청은 서로 독립이 아닐 수 있다. p값보다 실행 단위의 효과 크기와 일관성을 우선한다.
- 제외한 데이터는 기준과 건수를 적는다.
