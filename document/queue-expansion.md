# 대기열 3건 → 10건 확장 — 수정 사항 · PPT 구성

- 작성: 2026-11-04
- 기준 코드: `lgk-refactor` 브랜치, fault 중 접수 중단(`9ec25a8`) 반영
- 확인 방법: 코드 분석. 실제 실행으로 재현하지는 않았다.
- 대상: `MAX_QUEUE_LEN`(`config.py:33`). 조립대 3칸과 AGV 1대는 그대로다.

## 요약

코드 변경은 상수 한 줄이지만 **처리량은 그대로이고 대기 주문만 늘어난다.** 핵심 문제는 대기시간과 추월이다.

| 구분 | 3건 | 10건 |
|---|---|---|
| 최대 대기 주문 | 3건 | 10건 |
| 진행 포함 최대 주문 | 6건 | 13건 |
| 마지막 손님 대기시간 (조립대 점유 8분 가정) | 약 8분 | 약 27분 |
| 동시 처리 | 조립대 3칸 · AGV 1대 | 동일 |

대기시간은 `순번 × 점유 시간 ÷ 조립대 3칸`으로 낸 하한이다. 8분은 가정값이므로 실측으로 바꿔야 한다.

## 수정 사항

### 1단계: 동시성 먼저

| 작업 | 위치 | 내용 |
|---|---|---|
| 접수 순서 수정 | `routes/order.py:196` | 주문 해시 생성 뒤 `rpush` |
| 배정 락 | `services/dispatch.py` | `SET NX EX`로 배정 전체를 감싼다. TTL은 Mobius 최대 8초보다 길게 |
| 워커 전환 | `Dockerfile` | `--worker-class gthread --threads 8` |

순서를 지킨다. 락과 접수 순서 수정 없이 워커만 바꾸면 7번, 8번 경합이 실제로 발생할 수 있다.

### 2단계: 대기 경험

**예상 대기시간**

```
예상 대기 = 내 앞의 막히지 않은 주문 수 × 최근 배정 간격 중앙값 + 배정~도착 평균
```

| 작업 | 내용 |
|---|---|
| `assigned_at` 기록 | 지금은 배정 시각이 저장되지 않는다. `_assign`에서 남긴다 |
| 간격 집계 | 대기열이 비었거나 고장으로 멈춘 시간은 뺀다. 영업 초반은 기본값 사용 |
| 표시 | "약 20~30분"처럼 범위로. 막힌 주문은 "재고 보충 대기 중", 정지 중은 "라인 점검 중" |

**알림 · 취소**

| 작업 | 내용 |
|---|---|
| "곧 차례" 알림 | 배정 직전 손님에게 안내해 노쇼를 줄인다 |
| 손님 취소 | `abort_order`의 `queued` 경로 재사용. 본인 주문만 취소되도록 확인 |

### 3단계: 운영 안정성

| 작업 | 내용 |
|---|---|
| 고장 알림 | 관리자에게 바로 가는 소리 · 메시지 알림 |
| 상한 운영 중 조절 | `MAX_QUEUE_LEN`을 Redis 값 + 관리자 API로 |
| 지표 기록 | 접수~배정 시간, 예상과 실제의 차이, 취소율, 노쇼율, 추월 횟수 |

### 4단계: 추월 제한 · 복구

**추월 제한**

막힌 주문은 재고가 돌아오면 이미 맨 앞에서 먼저 배정된다. 우선순위를 올려도 빨라지지 않으므로, 할 수 있는 건 **관리자 알림과 뒷 주문 대기**다.

| 추월 횟수 | 막힌 원인 | 동작 |
|---|---|---|
| 2회 이상 | 전부 | 관리자 화면 경고 |
| 3~4회 이상 | `count_0`, `empty` | 뒷 주문 배정을 멈추고 보충 대기 |
| 횟수 무관 | `driver_failed`, `disable` | 멈추지 않고 경고와 중단 안내 |

횟수는 배정 성공 뒤에만 올린다. 스캔마다 세면 실제 추월 없이도 올라간다. 선반 고장은 수리 시간을 알 수 없어 멈춤 대상에서 뺀다.

```python
skipped = []
for order_id in r.lrange(QUEUE_KEY, 0, -1):
    ...
    blocked = stock.blockers(order_id)
    if not blocked:
        assigned = _assign(order_id, station_id)
        if assigned:                          # 롤백되면 세지 않는다
            for oid in skipped:
                r.hincrby(f"order:{oid}", "overtaken", 1)
        return assigned
    if _must_hold(order_id, blocked):         # 횟수 초과 + 보충 가능한 원인
        return None
    skipped.append(order_id)
```

## 보류: SSE

폴링을 SSE로 바꾸는 작업은 지금 넣지 않는다.

- 현재 sync 워커에서는 연결 하나가 워커를 점유해 서버 전체가 멈춘다.
- 워커 변경, Redis Pub/Sub, 재접속 처리, Flutter 수신 구현이 모두 필요하다.
- Cloud Run 요청 타임아웃으로 연결이 주기적으로 끊긴다.
- 조회 지연의 원인은 폴링 횟수보다 워커 구조이므로 gthread 전환을 먼저 한다.

**재검토 기준:** 폴링 주기가 1초 이하이거나 즉시 알림이 꼭 필요할 때.
